## 1. What this is

**TIFO Sports Manager** — a multi-sport club management simulation. Football is the real product:
Spring Boot 3.3.3 / Java 21 REST API with a vanilla-JS ES6-module frontend served from the same
application. PostgreSQL in production, H2 in-memory under the `test` profile.

Scale: **48 countries × 31 divisions × 10 clubs ≈ 14,880 clubs**, 96 national sides, a promotion
ladder per country, three tiers of international club cups. **723 main Java files / ~94k lines**,
**78 JS files / ~149k lines**, **157 test classes**.

The architecture is genuinely good and unusual for this genre: **one match engine**
(`newLogic/sim/`), decomposed into small engines behind a single `MatchState`, seeded
deterministically from `fixture.getId()`, with `ProposalEngineIsTheOnlyFixtureProducerTest` acting as
a structural guard against a fourth engine growing beside it. That is a real moat — neither Sokker
nor Hattrick can hand you a reproducible seeded run, and every calibration you have is a committed
artifact because of it.

## 3. What a player actually gets today

Register → **wait for an admin to approve you in the community chat feed** → pick a sport → a
dashboard showing club, league position, next fixture, last three results and three buttons.

Then you can: set a formation and XI; edit a **per-slot × per-ball-state movement-rule table** (the
deepest screen in the game); run weekly training; promote and release juniors; open and close the
junior school; list and buy players; watch a replay; read a teletext results desk; view a league
table with Elo columns; set stadium capacity and pricing; read a medical board.

**That is a real football manager, further along than the debt suggests.** The replay viewer, the
tactic editor, the transfer-negotiation rows and the presence counter are all above prototype
quality.

### Where it breaks

- **Two of the fourteen club screens show "API Error" for every manager whose club id is not 1.**
  `pages/features/club-management.js:44` and `pages/features/staff-directory.js:100` both call
  `/demo/teams/${teamId}/profile` inside an unguarded `Promise.all`; `DummyDataController` only
  serves team 1. **Finances and Staff are dead pages**, and the real ledger / board-trust / FFP /
  wage-bill data behind them is never fetched. This is precisely the "green status is not evidence"
  shape the project's own rules describe.
- **Six routed pages point at the fake-data controller**, hardcoded to team 1 with "Omladinac FC" and
  "John Smith". Hidden from menus, alive as `window.*` globals (`pages.js`, `fixture-view.js`,
  `stats-view.js`).
- **The match viewer is an engineer debug view with dev buttons on the front door** — a seed input,
  "Generate Match", "Load JSON", `alert()` on every failure path, a Back button that full-reloads the
  app, and a 3D tab that silently shows *a different match* (`viewer3d.js` reads
  `/proposal/api/latest`, never a `matchId`).
- **Scouting has no screen.** `ScoutingController` exposes three routes; nothing in the frontend
  calls them.
- **The national-team election is fully built and cannot complete.** `ensureElection`'s only caller
  is `DatabaseInitializer`, which no longer runs at boot; `declare` has no UI and no job.
- **Season is not a season.** A fixture card renders `19:00` with no date. Deleting the calendar was
  a defensible decision; the consequence reads to a player as missing data rather than as a design.
- **Owner credentials are hardcoded in shipped markup** — `login.html:31,35` pre-fills
  `velibor@example.com / A12345!` on every deployment, and `home.html:65` prints the first 20
  characters of the JWT to the console on every lobby load.
- **A dead menu entry ships live:** `dashboard.html:40` calls `loadPage('clubProfileSettings')`, which
  has no case in the router, so it lands on "Page not found".

## 4. The multiplayer premise is currently unenforced — and this is *not* on the board

This is the most important finding of this review, and `kanban.md` does not name it anywhere. Cluster
C closed five real holes, but **nobody checked whether a manager can mutate another manager's club.**
Verified in source:

| Endpoint | Guard |
|---|---|
| `PUT /teams/{teamId}/lineup-template` — `TeamController.java:368` | **none** — no principal, no ownership check |
| `PUT /teams/{teamId}/tactics-editor` — `TeamController.java:446` | **none** |
| `POST /teams/{teamId}/medical/recovery/{playerId}` — `TeamController.java:340` | **none** |
| every `/transfers/*` write | `teamId` is client-supplied and unverified |
| `POST /simulation/week/advance` — `SimulationController.java:219` | **no `@PreAuthorize`** — any authenticated manager advances the world a week |

`PlusFeatureService.isOwnTeam` **already exists** and is already correctly used in exactly four
controllers: `TrainingController:236`, `JuniorController:35`, `JuniorSchoolController:45`,
`StadiumSettingsController:64`. It is a one-line guard per method.

**A player can rewrite a rival's starting XI and tactical system by editing a URL.** In a game whose
entire premise is manager-versus-manager, that is the gap that matters most, and it is server-side.

Compounding it: `TeamController.java:248,263` compares a `CTeam` id against a `newLogic` `Team` id —
**two different id spaces**. So `resultHidden` / the reveal flow is effectively inert for every real
manager, and the "watch it or just read it" choice the whole match-week design is built around never
appears.

Also: `SimulationController:344,381` uses `teamRepository.findByName(...)`, which **throws on a
duplicate name**, while `TeamRepository`'s own contract allows duplicates and
`RegistrationService:149` requires the `CTeam` and `Team` names to be identical. Two clubs called
"OFK Beograd" would break *Prepare your match* and *Advance Week* for the affected manager.

## 5. The engine as football — assessment

### What is genuinely good

- Clean engine decomposition: adding an engine means adding a class, not editing a god class.
- Added time and half-time are modelled properly (`MatchOrchestrator:714-759`, `StoppageClock`).
- Determinism from `fixture.getId()`, with the `Random` first-narrow-draw bias found and fixed at the
  source in `SimulationRandom.seed()`.
- `GoalkeeperEngine` positioning is a real angle-narrowing model with graded, skill-scaled,
  speed-penalised saving, plus a correct trajectory gate (`onTrajectoryForGoal`).
- Playmaking-gated option **perception** (`CleanDecisionEngine:1060-1068`) is the right answer to
  "skill should change how many options exist".
- `readIntercept` decided once per defender per pass and cached — a correct fix found by measurement.
- `ProposalPassFailDiag` is the correct instrument for this class of problem.

### The five things that matter, in order

#### 1. The geometry is anisotropic and not metric — and the goal mouth is 1.4–1.9× too wide

`Position` is `(double row, double column)` on a 7 × 6 cell grid (`PitchEnvironment:10-15`). Length is
calibrated at **14 m per cell** — `GROUND_DECEL = 0.08` with the comment "~0.5 m/s²" checks out
exactly (`0.08 × 14 / 1.5² = 0.498`), and `MAX_BALL_SPEED = 1.5` cells/tick = 14 m/s checks out too.
Width is calibrated by **nothing**: two comments in the codebase disagree by 40%
(`BallPhysicsEngine:41` and `DuelEngine:19` say "1 cell = 14 m"; `CleanDecisionEngine:317,1021` say
"a cell is 14 m × 10 m").

| Feature | Engine | Real | Error |
|---|---|---|---|
| Pitch length | 98 m | 105 m | −7% |
| Pitch width | 84 m *or* 60 m | 68 m | +24% / −12% |
| **Goal mouth** | **14 m or 10 m** | **7.32 m** | **+91% / +37%** |
| Post radius | 0.42 m | 0.06 m | ~7× |
| Penalty area | 42 × 21 m | 40.3 × 16.5 m | width ok, depth +27% |
| Centre circle, corner arcs, six-yard box | **not modelled** | — | — |

Every radius in the engine — `ON_BALL_EPS`, `RECEIVE_R`, `INTERCEPT_R`, `DEFLECT_R`, `SHOT_BLOCK_R`,
all five duel radii, both press ranges, `MIN_PLAYER_DISTANCE` — is an isotropic Euclidean distance in
a space whose two axes have different metre scales. **A 0.35-cell reach is ~4.9 m along the pitch and
~3.5 m across it.** Nothing in the model can express that.

Direct consequence: on-target shots are aimed uniform in the mouth, and a shot within
`POST_RADIUS + BALL_R` of a post is deflected — **~10% of on-target shots hit the woodwork against a
real ~4%.**

**Fix the coordinate system to true metres (105 × 68, mouth 7.32 m, posts 0.06 m) before any other
realism work.** Every other number in this section inherits it.

#### 2. Reception is a 4-metre geometric coincidence, not a skill test

`RECEIVE_R = PICKUP_R = 0.35 cells` (`BallPhysicsEngine:67,72`) ≈ 3.5–4.9 m — two to four times a
real first-touch reach. If the flight *segment* passes within it, the receiver controls the ball. No
probability, no control roll, no first-touch skill test.

Worse: `ExecutionQuality.evaluatePass:82-83` computes
`overspeed = max(0, desiredSpeed − ballSpeedForSkill(passing))` — and `ActionExecutor:112` passes
`desiredSpeed = ballSpeedForSkill(passing)`. **`overspeed` is therefore always 0, `maxDeviation` is
always exactly 0.02 cells, and passing skill has *zero* effect on pass accuracy.** A skill-1 passer
and a skill-20 passer deviate identically. Aggregate pass accuracy lands near-real (~81%) for entirely
the wrong reason.

The two layers also disagree about what a passing lane is: the decision layer's `laneBlockPenalty`
corridor is **0.35 cells** (`CleanDecisionEngine:912`) while the physics layer's `INTERCEPT_R` is
**0.14** (`BallPhysicsEngine:68`). A pass the AI scores as having a clear lane can still be read by
a defender two metres off the line.

#### 3. Only one designated presser can ever take the ball

`MovementEngine` enforces `MIN_PLAYER_DISTANCE = 0.35` (`:23`) against **every** player, including the
presser. `DuelEngine` radii: DRIBBLE `0.15`, DRIBBLE-vs-presser `0.38`, RECEIVE_PASS `0.20`,
SHOT_BLOCK `0.30`.

- A **non-presser** defender is parked at ≥ 0.35, so 0.15 / 0.20 / 0.30 are all **geometrically
  unreachable** — no duel fires at all.
- A **presser** is parked at exactly 0.35, which is *inside* 0.38, so the press duel always fires.

**The only route to dispossessing a carrier in this engine is the single TYPE A presser. One defender
in the entire match can contest a dribble.** Real football has two to four converging.

This is the root of the duel-count saga recorded in the board (713 → 358 → 373 → 268 against a real
~100) and it is **structural, not a tuning problem**. Two further defects in the same area:
`DuelType.TACKLE` is never returned by `checkDuel` (dead), and `AERIAL` / `HEADER` exist with
`AERIAL_DUEL_RADIUS = 0.5` but `checkDuel` has **no aerial branch** — so a cross into a packed box is
resolved by 2D distance alone.

#### 4. Two of three shot-model inputs are dead, and the distance falloff is far too flat

`ExecutionQuality.evaluateShot:134-217`:

```
skillBase  = 0.06 + skill × 0.015
distFactor = max(0.25, 1 - dist/9.0)
onTarget   = skillBase × distFactor + (dist<2.0 ? 0.08 : 0) × (1 - pressure/200)
```

- **`pressure` is passed as the literal `0.0`** from `ActionExecutor:292`. The pressure term never fires.
- **`confidence` is always exactly 1.0** — `setConfidence()` is never called anywhere in `src/main`, so
  `confidenceModifier()` is a constant and the entire morale→finishing chain inside a match is inert.
  (Morale is applied *after* the match, in `SimMatchService.bumpCareerStats`.)

On-target rate for a skill-16 striker:

| Distance | Engine | Real | Ratio |
|---|---|---|---|
| 14 m | 34.7% | ~25% | 1.4× |
| 21 m | 33.0% | ~9% | 3.7× |
| 28 m | 23.3% | ~4% | 5.8× |
| 35 m | 16.7% | ~1.5% | **11×** |

The `dist/9.0` divisor is far too flat — a 50% falloff needs ~4.5 cells.

Also: off-target shots are **always both wide and short** (`:196-209`), so no shot ever goes over the
bar and no miss is ever narrow. `POST_HEIGHT_M = 2.44` is stored and **never read** — there is no ball
height, no crossbar, no header, no aerial ball anywhere in the engine. On-target aim is uniform across
the whole mouth despite the comment claiming "real shots on frame go to corners", so 33% of on-target
shots land centrally, exactly where the keeper stands.

#### 5. Offside is not applied to through balls, crosses or centres

`MatchOrchestrator:431-443` gates the check on `ActionType.PASS` **only**. `THRU`, `CROSS` and `CENTER`
execute with no offside check at all, and no `offsideFlaggedReceiver` is ever set for them.

`scoreThruOptions:575` self-protects (`offsideMargin <= 0`) — but `scoreBoxDelivery:634-686` does
**not**: it picks the best attacker in the box by `striker × 1.2 + technique × 0.8` with no offside
consideration whatsoever. **A cross into a crowded box to a forward one metre beyond the last
defender is completely legal.** Deliveries are the single largest offside source in real football.

Also: the tolerance is far too generous — `OFFSIDE_WHISTLE_MARGIN = 0.30` cells ≈ 3–4.2 m against a
real tolerance of a foot plus a ball radius. And there are **two different offside lines in the same
match**: `OffsideService:300`, `CleanDecisionEngine:700,896` include the goalkeeper (correct, per Law
11) while `ThreatOverrideEngine:231-240` explicitly filters the GK out — so the TYPE C retreat trigger
is computed a defender further up the pitch than the line the referee uses.

### The rest, as a football analyst

- **No set-piece decision logic at all.** `ActionType` declares `THROW_IN`, `GOAL_KICK`, `FREE_KICK`,
  `CORNER`, `KICK_OFF` — and `CleanDecisionEngine` **never returns any of them.** A corner with nobody
  in the engine's box becomes a sideways pass out of play. Free kicks have a "wall" of 0.65 cells
  (~9 m) pushed by `pushOpponentsAwayFromBall`, no distance, no attempt, no routine.
- **No marking assignments.** `closestMarkerTo` finds the nearest opponent *to decide whether to avoid
  a pass*; no defender is ever assigned to anyone.
- **No game-state management.** The scoreline reaches exactly **one** place in the whole engine
  (`ConditionalSubstitutionRules`). No chasing a game, no protecting a lead, no time-wasting.
- **No in-match morale** (see #4) and **no momentum**.
- **Formation is always 4-4-2.** `TacticsRules.FORMATION = "4-4-2"`; `FormationSlotCatalog`'s 9 layouts
  are unreachable; the 6 tactic slider fields have zero readers. All **506 out-of-possession tactical
  rules are byte-identical** to their in-possession twins, so `DefensiveShape` does 100% of the
  defensive work — one shape, no press, no mid-block, no low block.
- **21 of 22 players are quantised to 42 static anchors.** The tactical lookup resolves
  `7 × 6 = 42` discrete ball-state cells with **no interpolation**, and `MovementEngine` clears the
  target on arrival so outfielders are near-static. The only continuously-moving targets in the engine
  are the ball, the carrier, the keeper, the loose-ball chaser and the single presser.
- **Players cover ~26.5 km per match** (real ~11). `pace/20 × 0.75` cells/tick used as a *sustained*
  speed for 90 minutes, with no walking or jogging state. The keeper factor `1.9` puts a keeper at
  ~26 km against a real 4–6 km.
- **Fatigue is inert for the shipped squads.** `DRAIN_PER_CELL = 0.00035` × stamina factor gives a
  peak fatigue of 0.20–0.26, so `FATIGUE_SUB_THRESHOLD = 0.62` **never fires** — the fatigue
  auto-substitution path is dead — and `InjuryService:119`'s fatigue term is **exactly 0**, so the
  "tired player is the one who goes down" chain never fires either.
- **Substitutes are reported as playing 90 minutes** (`ProposalStatsCollector:363-368` ignores the
  `cameOnTick` / `wentOffTick` maps that `MatchState` maintains).
- **MOTM is effectively "most passes completed"** — the rating formula has no shot term, no
  progressive-pass term, no team-result term and no availability term.
- **xG is a six-band distance lookup applied post hoc, with a bug:** it measures to column **3.5 (the
  left post)** instead of 4.0 (the mouth centre), so every shot left of centre is understated and every
  shot right of centre overstated — a systematic left/right bias. No shot angle, no blockers, no
  keeper, no pressure, no body part, no penalty/open-play split.
- **Every random draw in the engine is `nextDouble() < p`** — a Bernoulli. There is no Gaussian,
  Poisson, exponential, gamma or beta anywhere; all continuous quantities are uniform on a range.
- **A database connection per match:** `new TacticsRules()` → `loadFromDb` opens a raw JDBC connection
  to `localhost:5432` on **every simulated match**, uncached.
- **Thread-safety defect:** `ActionLogService.fileLog` is a `static` `PrintWriter` for the whole JVM,
  written outside its own lock, with **no match identifier in the line prefix**. The engine's own docs
  say it emits ~28,000 tagged lines per match. Parallel matches interleave into an unparseable log.
  `OffsideService.TRACE` is a `public static boolean` global.
- **~60 uncalibrated magic numbers live in javadoc blocks on `private static final` fields**, each
  tuned in isolation against a moving codebase, with **no shared baseline document and no regression
  test asserting any of them still holds.** `kanban.md:545` says explicitly that the numbers on the
  realism board *"were measured against code that has since changed"* — so **re-baseline before
  accepting any headline figure in those comments.**

### Performance, for scale

~0.3–0.6 s of single-core CPU and ~11 MB retained per in-flight match (83k snapshot objects plus 28k
log strings, all held for the whole match before any downsampling). At 155 fixtures per matchday that
is ~78 s of CPU across cores. **The 2 h 52 m full-suite runtime is dominated by database I/O and JPA
persistence, not by the engine** — `ZoneLoadRecorder` alone saves ~121 rows per match, one at a time,
and `IDENTITY` generation on 70 of 71 entities means no JDBC batching to make it cheap.

## 6. What I would do, in order

I disagree with the board's ordering. It wants D (scale) and E (tests) next. **I would do neither
first.**

### P0 — this week (hours, not days)

1. **Ownership guards** on `lineup-template`, `tactics-editor`, `medical/recovery`, every
   `/transfers/*` write, and `@PreAuthorize` on `/simulation/week/advance`. `isOwnTeam` already
   exists and is already used in four controllers. *Without this you do not have a multiplayer game;
   you have a database with several browsers pointed at it.*
2. **Delete `DummyDataController` and its six frontend call sites.** Two working pages are dead because
   of it. One commit, no risk.
3. **Fix the `CTeam` / `Team` id-space collision** (`TeamController:248,263`) so result-hiding
   actually engages — it is the mechanic the whole match-week design is built around and it has never
   fired for a real manager.
4. **Remove the credentials from `login.html:31,35`** and the JWT prefix `console.log` in
   `home.html:65`. Delete the dead `clubProfileSettings` menu entry.

### P1 — the next two weeks

5. **Convert the engine's coordinate system to true metres.** 105 × 68, mouth 7.32 m, posts 0.06 m,
   and a real z axis for ball height. This is the prerequisite for every realism item below, and it
   invalidates every calibration number currently in the codebase — which is exactly why it must come
   *before* re-baselining rather than after.
6. **Offside on `THRU` / `CROSS` / `CENTER`, one offside line, real tolerance** (foot + ball radius,
   not 3–4 m).
7. **Pass completion as a skill test**, not a 4 m coincidence — and make passing skill actually move
   deviation. Reconcile the 0.35 decision corridor with the 0.14 physics interception radius.
8. **Fix the dispossession geometry** so two to four defenders can converge, then re-measure duels
   against a real ~100. Delete the dead `TACKLE` type; give `AERIAL` a branch or delete it.
9. **Wire pressure and confidence into the shot model, or delete both terms honestly**, and re-fit the
   distance falloff against a shot-distance distribution instead of `dist/9.0`.
10. **The viewer: hide the dev panel, replace `alert()` with real error states, gate the 3D view on a
    `matchId` or remove it, and wire or delete `ZoxReplayController`'s chunked transport.** The
    product's headline feature currently has three broken edges and a developer-tools panel on its
    front door.

### P2 — the month

11. **Game state (chasing a game, protecting a lead, time-wasting) plus real set-piece routines.**
    These two are what separate a simulator from a football game, and **neither exists**.
12. **Honest analytics from the same tick data that drives the animation** — xG from the shot model
    rather than a six-band distance table, plus xA, PPDA, field tilt, progressive passes and distance
    covered. The differentiator is that the numbers and the pictures **cannot disagree**, and
    determinism makes every figure recomputable and checkable. That is a genuine moat and it is the
    largest single product gap on the board.
13. **A pre-match preview computed from `ScheduleInsightService`**, which already does the job the
    page claims to do. Today `zox-match-preview.js` shows `drawProbability = 0.25`, formation fitness
    `0.92`, availability `95` as constants, and `homeTeamRating` / `awayTeamRating` are averages of
    **post-match** `MatchPlayerStats.getRating()` — the page's "prediction" analyses the match that has
    already been played, and defaults to `localStorage.lastMatchId`. **Either compute it or delete the
    page.** A wrong number dressed up is worse than a missing one.
14. **Retirement age** (one day, and without it neither the pyramid nor the market can turn over), then
    board sacking, then expose `NegotiationService.acceptOffer(transferId, offerId)` — the service
    already correctly rejects every other offer and **no controller exposes an `offerId`**. The
    cheapest fix in the whole transfer area.

### What I would deliberately *not* do yet

**Cluster D (scale).** Every measured cost is seconds, not minutes. `FinanceJob`'s ~14,880
`REQUIRES_NEW` transactions is inherent to the per-club isolation the class documents as deliberate.
At 14,880 clubs with **two active countries**, this is complexity paid for a world nobody plays in.
**Activate more countries before optimising for them.** Do the cheap half only: **keyset paging on
`findLoadsPlayedSince`** — offset paging over a join with no total order can skip and duplicate rows,
which would silently under-count a player's recovery, the exact bug class this board exists to stop.

**A full `mvn test` as a gate.** 2 h 52 m, needs the app on :8080, and `GameClockDateFollowsGameTimeTest`
plus `SeasonRolloverNumberTest` advance the clock, which fires the matchday jobs and simulates **986
matches between them**. Two baselines are only comparable if they were measured the same way.

## 7. Three standing observations

**The most valuable thing in this repository is not the engine — it is the discipline.** Mutation-verified
guards, measured claims, honest logs that say "this is deliberately not done". That is rarer than the
code, and it is worth more than any feature on the roadmap. The board's own lesson is correct: A4 and
A5 were the two highest-ranked items in two separate audits, and **one test run proved neither existed.**
Keep measuring before editing.

**The documentation is now the largest single liability.** 18,742 lines of root markdown describing a
94k-line codebase, with three files actively misleading (`sprintBacklog.md` still claims five deleted
stub services that exist and prints "Sprint 5 ◀ CURRENT" twice; `PROPOSAL_CURRENT_STATE.md` lists two
solved P0s as OPEN; `expertAudit.md` is superseded). Every one of the four "defects" I would have fixed
from reading alone this session turned out to be already fixed. **Consolidate on the kanban pair and
archive the rest.**

**Football-wise, the gap is not statistics — it is decisions.** There is no marking, no game state, no
set pieces, no aerial duels, one presser, and 42 movement anchors. The headline numbers are wrong in
ways that will all move once the geometry is fixed anyway. **Fix the pitch, fix who can win the ball,
fix the offside rule on deliveries — then re-baseline.** In that order.
